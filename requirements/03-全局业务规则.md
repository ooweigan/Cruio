## 1. 文档权威与使用方法

### 1.1 规则层级

1. 《01-总PRD.md》定义产品目标、完整范围、模块边界和版本方向。
2. 本文是跨模块术语、业务规则和责任约定的唯一主责文档。
3. 分模块 PRD 负责模块内功能、页面、状态、异常和验收，只能引用 GLB-*，不得创建含义相反的“局部全局规则”。
4. 《02-调研证据与对标.md》支撑外部事实，但不直接批准产品决策。
5. 若分模块设计发现规则不适用，应记录冲突、影响和建议方案，按本文第 12 节处理；在总纲和本文更新前，不自动生效。

### 1.2 规则状态

| 状态 | 含义 | 下游使用方式 |
|---|---|---|
| 用户已明确 | 用户已直接确认的约束 | 必须遵守；改变时需进入需求变更流程 |
| 设计基线 | 当前推荐并可继续细化的统一方案 | 分 PRD 按此起草，同时保留评审权 |
| 设计建议 | 存在其他可行选项，本文给出推荐 | 下游不得写成已批准，须保留决策状态 |
| 未来规则基线 | 适用于尚未启用的订单、支付、分销等完整范围 | 首发不启用，但后续设计不得与其冲突 |
| 待确认 | 缺少业务决策、法律结论或外部能力核验 | 不得开放相关能力或假定结果 |

### 1.3 事实主责原则

每个业务对象和关键状态只设一个事实主责模块。其他模块可以：

- **查看**：按权限读取业务事实；
- **申请**：提出业务变更请求，由主责模块判断并产生结果；
- **订阅变化**：接收主责模块确认后的结果，用于展示、通知或后续处理；
- **不得直接修改**：不能绕过主责模块直接改状态、余额或历史记录。

管理后台、通知、客服和报表是横向入口或消费者，不因“能看到／能操作”就成为源业务事实的所有者。

## 2. 统一术语表

完整领域语言以 [《CONTEXT.md》](../CONTEXT.md) 为准。本节列出后续分 PRD 最容易混淆、必须统一使用的术语。

### 2.1 身份与权限

| 术语 | 统一定义 | 必须区别 |
|---|---|---|
| 用户 | 具有稳定账户身份、可以拥有资源和被授予角色的个人 | 不等于管理员、老师或创作者等角色 |
| 游客 | 尚未登录、只能访问允许公开内容的访问主体 | 不拥有私有项目、素材、作品、积分或学习进度 |
| 角色授予 | 用户在特定范围内获得的管理员、运营、分销者、老师、学员或创作者职责与权限 | 角色可叠加、撤回和限定范围，不是互斥账户类型 |
| 运营岗位 | 运营角色的细分职责，例如模型、积分、内容、课程、客服或审核 | 不存在默认“全能运营” |

### 2.2 模型与供应

| 术语 | 统一定义 | 必须区别 |
|---|---|---|
| 模型厂商 | 对模型或云端服务承担官方发布责任的主体 | 不等于本产品实际采购渠道 |
| 供应渠道 | 本产品实际采购并调用某一模型能力的来源 | 同一模型可能有多个渠道，能力、条款和价格不同 |
| 模型系列／展示名 | 面向用户认知或营销的一组名称 | 不能直接作为可执行标识 |
| 精确模型／版本 | 某渠道下可执行的准确模型标识或快照 | 只有核验后才能开放 |
| 能力快照 | 特定时间点下某渠道与精确模型组合的输入、输出、参数、任务、地区和厂商资产能力 | 不等于永久能力承诺 |
| 采购成本参考 | 特定渠道能力在某时点的成本依据 | 不等于面向用户的积分报价 |

### 2.3 文件、素材、厂商资产、输出与作品

| 术语 | 统一定义 | 必须区别 |
|---|---|---|
| 文件 | 承载图片、视频、音频或文本的数字载体 | 文件只有获得归属、用途和授权语义后才成为业务素材或作品文件 |
| 素材 | 作为创作输入管理的私有或平台参考内容 | 不等于任务输出或作品 |
| 平台素材 | 平台在明确授权范围内提供给用户使用的素材 | 不默认可公开、转售或脱离指定场景复用 |
| 厂商资产 | 某素材在特定厂商／渠道登记后形成的外部资产身份和状态 | 不等于本产品永久保存了原素材，也不等于厂商确认权属 |
| 任务输出 | 工具运行或生成任务产生、尚未被用户保存为长期作品的结果 | 不自动成为素材或作品 |
| 交付副本 | 本产品已可靠取得、在承诺期限内可供用户访问的任务结果 | 不等于用户已经保存作品 |
| 作品 | 用户主动确认长期保存的图片或视频成品，默认私有 | 不等于任意输出或公开内容 |
| 分享授权 | 允许特定链接、用户或受众受控访问私有作品的权限 | 不等于公开发布 |
| 发布记录 | 作品进入公开展示、改变公开范围或撤下的事实 | 不等于作品本体；撤下不等于删除私有作品 |

### 2.4 画布、工作流与任务

| 术语 | 统一定义 | 必须区别 |
|---|---|---|
| 画布文档 | 用户当前可编辑和恢复的空间布局与创作上下文 | 不等于工作流运行或生成任务 |
| 画布节点／任务卡 | 画布上的内容、素材、工具、任务投影或结果单元 | 显示状态不是 M04 的任务事实 |
| 工作流定义 | 节点、连接、输入输出关系和执行顺序构成的创作结构 | 不等于工作流运行 |
| 工作流版本 | 某次运行或历史恢复所引用的定义快照 | 后续编辑不得改写历史运行 |
| 项目画布 | 单个项目的创作布局与上下文，可引用工作流版本 | 不等于工作流定义的编辑图 |
| 项目工作流引用 | 项目对有权访问的明确工作流版本的绑定 | 不转移工作流所有权；源定义更新不静默改写已绑定版本 |
| 工具定义／版本 | 封装某项用户任务及其输入、参数、处理规则和输出约定 | 不等于模型或工具运行 |
| 工具运行 | 用户确认执行某工具版本的一次业务事实 | 不等于工具节点 |
| 工作流运行 | 用户确认执行某工作流版本后形成的一次整体过程 | 可包含多个节点运行 |
| 节点运行 | 工作流运行中某个可执行节点的一次执行事实 | 可关联一个或多个生成任务，具体规则由 M04 定义 |
| 生成请求 | 用户确认并通过前置校验、准备提交的创作意图快照 | 不等于页面上的每次参数编辑 |
| 生成任务 | 对外部模型／渠道的一次可跟踪执行事实 | 独立于页面和任务卡生命周期 |
| 执行日志 | 面向用户和运营可核查的过程摘要 | 不暴露供应商密钥、内部审核阈值或无关敏感数据 |

### 2.5 积分、货币、权益与佣金

| 术语 | 统一定义 | 必须区别 |
|---|---|---|
| 积分 | 用户在产品内使用生成能力的额度权益 | 不是货币余额，也不是佣金 |
| 积分账户 | 用户积分权益的汇总视图 | 余额必须能由积分账本解释 |
| 积分账本 | 获得、预占、消耗、退回、到期、调整和冲正的不可覆盖事实 | 不能直接改余额来代替账本 |
| 生成报价 | 提交前基于当时工具、模型能力和报价规则形成的预计积分消耗 | 不等于最终实结或采购成本 |
| 货币支付 | 未来订单中通过支付渠道形成的交易事实 | 不等于积分到账或课程权益到账 |
| 权益 | 用户被允许访问、使用或消费某项能力的业务资格 | 不等于付款成功或角色授予 |
| 会员权益 | 在有效期内按会员规则组合授予的多项权益 | 不自动等于积分、课程权或无限生成 |
| 课程权益 | 访问指定课程／课节的学习资格 | 不等于生成额度 |
| 模板使用权 | 查看、实例化或在限定范围内复用某模板的资格 | 不等于模板所有权或素材复用权 |
| 练习素材使用权 | 在指定课程或练习场景中使用素材的范围性授权 | 不等于素材所有权或公开复用权 |
| 生成额度 | 可用于工具运行或生成的积分或其他受限额度 | 不等于课程权或会员身份 |
| 佣金 | 基于合资格推广归因和真实订单形成的待确认或可结算收益义务 | 不进入积分账本，不等于现金余额 |

## 4. 业务对象主责矩阵

### 4.1 身份、创作与内容对象

| 业务对象／关键状态 | 定义与修改主责 | 可申请变更 | 可查看／订阅 | 禁止越界 |
|---|---|---|---|---|
| 用户、账户状态、角色授予、资源所有者 | M02 | 用户发起账户操作；M11 按权限申请后台角色变更；业务模块申请业务身份关联 | 其他模块按最小必要范围查看身份、角色和归属 | 业务模块不得自行创建管理员权限或改变资源所有者 |
| 项目、画布文档、工作流定义／版本、节点／连接 | M01 | 用户或被授权老师／运营按作用域操作 | M04 查看执行所需快照；M12/M13 查看摘要 | M04 不回写画布定义；任务状态只以投影方式呈现 |
| 工具定义／版本／发布状态 | M01 | 运营通过 M11 发起发布、下线或变更 | M03/M04/M07/M14 查看兼容、执行、报价与安全信息 | 工具更新不得静默改变历史运行 |
| 工具运行、工作流运行、节点运行、执行日志 | M04 | M01 发起；用户申请取消或重试 | M01 显示投影；M07 结算；M12 通知；M13 汇总 | M01 删除节点不得删除运行事实；日志不得暴露敏感凭证 |
| 私有素材、平台素材、素材集 | M05 | 用户管理私有素材；运营申请平台素材发布／下线 | M01/M04 按授权引用；M06/M10 仅在明确授权下引用 | 作品模块不得把作品自动复制为平台素材 |
| 厂商资产登记、Asset ID、处理／可用状态 | M05 | 用户或运营发起登记、更新、撤回 | M03 提供能力约束；M04 提交前核验；M14 查看授权 | M03 不保存用户厂商资产实例；列表可见不得当作可用 |

## 5. 业务事件约定

### 5.1 事件使用原则

1. 业务事件表示“主责模块已经确认发生的事实”，不是页面点击、内部命令或技术消息。
2. 事件名称使用完成式语义，例如“积分已入账”，不使用含糊的“处理积分”。
3. 事件接收模块只能据此完成自己的职责，不得反向改写源事实。
4. 事件送达失败不等于源事实失败；接收方处理失败由接收方记录并进入补偿或人工待办。
5. 本节只约定触发、主责、接收、后果和补偿责任，不定义接口地址、消息结构或传输方式。

2. 下游主责模块保证自己的处理结果真实，并记录“未处理、处理中、成功、失败或需人工处理”。

4. M11 提供内部待办和受控操作入口，M12 负责用户沟通，M13 汇总差异，但三者均不替代交接双方修正源事实。

### 7.2 页面生命周期与任务生命周期（GLB-003）

2. 重新进入项目时，M01 应从 M04 获得最新可披露状态，而不是只恢复旧画布显示。
3. 删除任务卡仅影响画布展示；取消生成必须向 M04 单独申请并获得明确结果。
4. 项目归档不自动取消项目内运行；项目删除与仍在执行任务的处理规则须由 M01/M04/M14 明确后才可开放。

### 7.3 实际能力与供应商差异（GLB-010）

1. 只有厂商—渠道—精确模型／版本组合核验后，才可展示为可执行能力。
2. 参数、输入数量、厂商资产、同步／异步模式、进度、取消、重试和结果取得方式按能力快照呈现。
3. 供应商不支持的操作不得以灰色假按钮或虚假状态提供；用户可见能力应诚实反映实际限制。
4. M04 保留供应商原始状态和错误用于核查，同时向用户展示非敏感、可理解的产品状态。
5. 历史成功任务不能替代当前能力核验；渠道或版本变化后可退回“待核验”或暂停。

### 7.4 重复提交与重试（GLB-021）

1. 产品必须区分：用户再次点击、客户端重发、系统恢复提交、供应商重试和用户主动创建新任务。
2. 对同一已确认请求的重复操作，应先返回已有任务或要求用户明确创建新任务，不得静默重复扣费。
3. 当供应商是否已接受请求尚不明确时，不得盲目再次提交；先进入未知状态核查。
4. “重试”必须说明是继续查询原任务、对原任务重新取结果，还是创建新的供应商任务；只有新任务才可能产生新的报价和积分处理。

### 7.5 交付三阶段（GLB-008）

1. **供应商成功**：供应商报告任务完成或返回结果。
2. **交付副本已取得**：本产品已可靠取得并能在承诺范围内向用户提供结果。
3. **作品已保存**：用户主动将交付结果保存为长期作品。

三个阶段分别由 M04、M04、M06 主责。任何前一阶段成功都不自动等于后一阶段成功。临时供应商 URL 不得在未验证可持续访问时直接当作长期作品地址。

### 7.6 通知与事实（GLB-036）

1. 任务成功、积分入账、作品发布等事实由源模块确认；M12 只负责通知生成、送达、阅读和偏好。
2. 通知发送失败不回滚源业务事实；应允许用户在业务页面查看真实结果。
3. 用户未读通知不等于业务未完成；通知已读也不等于用户接受结果或放弃申诉。
4. 通知内容不得泄露敏感素材、密钥、内部审核阈值或其他用户信息。

## 8. 计费、积分与异常结算规则

### 8.1 成本与报价分责（GLB-005）

1. M03 维护采购成本参考及其适用渠道、模型和版本；M07 维护面向用户的积分报价规则。
2. 用户积分报价可以参考采购成本，但两者不等同，不得用同一字段或同一事实名称表达。
3. 每次可计费提交应能追溯当时的能力快照、成本参考版本、报价规则版本和用户确认的预计积分。
4. 后续价格调整只影响明确生效后的新报价，不重算已确认的历史请求。

### 8.2 报价确认（GLB-022）

用户在提交前看到预计积分和计费条件，并确认后才进入预占／提交。若输入、模型、关键参数或报价版本发生导致价格变化的修改，应重新报价并再次确认。

批量工作流未来可以让用户确认明确的总额度上限，但不得用设置页中的通用同意取代本次报价或额度上限确认。

### 8.3 预占与实结（GLB-023）

采用“预占后实结”：用户确认报价后，M07 先预占预计所需积分；M04 确认结果可靠交付、用户能够正常访问后，M07 再实结实际积分并释放差额。明确失败或最终无法交付时释放全部预占。

预占不是最终消费。用户同时提交多个任务时，各任务分别预占对应积分，已预占额度不能被其他任务重复使用。多个积分批次扣减顺序和到期处理仍由 M07 PRD 细化。

### 8.4 最终结算门槛（GLB-024）

只有 M04 确认交付副本已经可靠取得、用户能够正常访问时，M07 才最终扣除积分。供应商返回成功但结果尚未完成转存、关联失败或用户无法访问，不视为可靠交付。

若经核查确认平台最终无法交付，M07 释放全部预占，本次任务不产生实际扣分；当前不额外赠送补偿积分。M04 保留任务和故障事实。具体交付保留时长、转存恢复次数和不可恢复判定由 M04 PRD 细化。

### 8.5 失败、取消与未知状态（GLB-025）

| 任务／交付结果 | 积分处理基线 | 责任 |
|---|---|---|
| 提交前校验失败 | 不建立可计费任务；不预占或立即释放 | M01/M03/M05/M07/M14 返回可理解原因 |
| 明确提交失败且供应商未接受 | 释放全部预占 | M04 确认提交事实，M07 记账 |
| 供应商明确失败且无可用结果 | 释放全部预占 | M04 保留原始失败，M07 释放预占 |
| 用户请求取消且供应商确认未执行／已取消 | 按明确结果释放预占 | M04 确认取消事实 |
| 用户请求取消但供应商仍执行 | 不把“请求取消”当成已取消；按最终任务与交付事实处理 | M04 继续跟踪，M12 告知用户 |
| 供应商成功但交付转存／关联暂时失败 | 不最终实结、不释放预占，进入交付恢复／差异待办 | M04 恢复，M07 保持可追溯预占状态 |
| 经人工核查确认永久无法交付 | 释放全部预占，不产生实际扣分，不额外补偿积分 | M04 保留任务和故障记录；M07 释放预占 |
| 状态未知 | 继续保持预占；不最终扣分、不释放、不自动重提、不擅自判断成功或失败 | M04 持续核查；M11 承接人工处理，直至形成明确结果 |
| 重复提交被识别为同一请求 | 返回原任务，不新增预占／扣费 | M04/M07 保持单一事实 |
| 用户明确创建新的再次生成 | 形成新报价、新确认和新任务 | M01/M04/M07 各自留痕 |

未知状态不设置自动释放规则，持续保持预占直到人工核查并完成处理。核查操作权限、处理记录和供应商迟到结果的具体步骤由 M04/M07/M11 分 PRD 细化，但不得改变上述扣分原则。

### 8.6 结果转存与作品保存

1. 供应商结果转为交付副本属于 M04 交付责任，不是 M06 保存作品的责任。
2. 交付副本已取得后，用户未保存作品不影响已完成任务的积分结算。
3. 作品保存失败不得回滚已可靠交付的任务；M06 应允许在交付结果仍有效时重试保存。
4. 因平台转存、关联或保存等原因永久无法交付时，释放全部预占、本次不扣分且当前不额外补偿积分；任务和故障记录继续保留。

### 8.7 外部成交积分入账与冲正（GLB-006、GLB-007、GLB-026）

1. 线下财务、合同或第三方渠道订单确认外部成交后，有权限后管在 M11 登记凭据并发起积分入账；不在 M08 创建订单、支付或退款事实。
2. 入账记录必须关联目标用户、积分数量、成交渠道、外部订单号或合同号、付款／订单截图等凭据、操作人、操作时间和必要备注。
3. 付款／订单截图可能包含姓名、地址、账号等信息，产品应提示遮盖无关隐私，并限制后台查看权限。
4. 当前不建设线上审批流、双人复核或复杂审计系统；仍需保留操作者、操作时间、凭据关联、账本结果和必要的错误修正记录。
5. 只有 M07 生成账本条目后才算积分已到账；M11 不直接覆盖余额。
6. 错误入账不得删除或覆盖原账，通过反向冲正和必要的新正确记录修复。

### 8.8 外部退款扣回与负余额（GLB-037）

1. 退款由线下财务或第三方渠道人工处理；确认退款后，有权限后管在 M11 登记退款凭据并发起对应积分扣回。
2. 对应积分尚未使用且余额充足时，M07 直接扣回。
3. 积分已经使用或余额不足时，M07 允许形成真实负余额，不强制归零，也不删除历史消费记录。
4. 负余额用户暂停新的付费生成；无需积分的浏览、学习或其他能力是否受影响，由对应模块定义，不得一并封禁。
5. 用户后续获得新积分时，新增积分优先填平负余额，剩余部分才成为可用余额。
6. 当前系统只记录外部退款凭据和积分扣回结果，不提供产品内退款申请、审批或资金退回流程。

## 9. 订单、退款、佣金与权益规则

> 本节保留未来完整产品规则。当前只销售积分包，不启用会员、M08 线上订单／支付／退款或平台订单驱动的 M09 佣金，不得用手工订单模拟。

### 9.1 支付与权益到账（GLB-012、GLB-027）

1. 订单支付成功由 M08 主责；积分到账由 M07 主责；课程权益到账由 M10 主责；佣金形成由 M09 主责。
2. 支付成功后，M08 记录“应发权益”，但不得直接把其他模块状态标成已到账。
3. 一张订单可以包含多种权益；每种权益分别成功、失败、补发或撤回，并在订单履约摘要中显示。
4. 权益发放失败不自动把支付改成失败；由 M08 协调补发、换发或退款决策。
5. 通知用户“支付成功”时，应同时清楚显示权益是否已经到账，不用一个“购买成功”掩盖履约差异。

### 9.2 权益分类（GLB-028、GLB-031）

| 权益类型 | 主责 | 授予内容 | 不自动包含 |
|---|---|---|---|
| 积分／生成额度 | M07 | 在规则范围内用于工具运行或生成 | 课程访问、模板所有权、佣金 |
| 会员权益（未来） | M08 定义商品与有效期；具体权益由各主责模块落实 | 一组有期限的权益组合 | 当前不启用；未来也不自动包含无限积分、全部课程、永久价格或所有模型访问 |
| 课程权益 | M10 | 访问指定课程或课节 | 生成额度、模板复制、练习素材公开使用 |
| 模板使用权 | M01/M10 | 查看、实例化或按范围复用指定模板 | 模板所有权、来源素材复制、无限运行 |
| 练习素材使用权 | M05/M10 | 在指定课程／练习场景中使用素材 | 商业发布、脱离课程下载、公开再分发 |
| 作品／案例复用权 | M06/M14 | 按授权查看、引用或创建新项目 | 原提示词、私有素材、完整画布全部开放 |
| 分销资格 | M09 | 使用推广标识并查看本人归因 | 自动产生佣金、课程权或创作积分 |

当前不建设会员订阅、会员等级、周期性赠送积分、会员专属模型、会员课程包或无限生成权益，只销售积分包。未来是否引入会员，依据真实复购和用户使用频率重新评估；若启用，会员仍是明确权益组合，不是万能权限。

### 9.3 退款与权益回收（GLB-029）

以下仅为未来启用 M08 时的候选平台退款方案，当前不做选择，也不进入产品功能：

| 方案 | 说明 | 优点 | 风险 | 建议 |
|---|---|---|---|---|
| A. 未使用权益可退，已使用部分按规则扣除 | 区分未使用与已消耗权益 | 相对公平，可核查 | 需定义使用认定和组合商品分摊 | **推荐起点** |
| B. 在法定／约定期限内整单退款 | 满足条件即整单退 | 用户简单 | 已消耗权益、课程观看和佣金处理复杂 | 仅用于适合商品 |
| C. 数字权益一经发放不退 | 发放即不可退 | 运营简单 | 可能与地区规则冲突，用户争议高 | 不作为全局默认 |

无论选择何种方案：

1. M08 记录退款事实；M07/M10 分别记录积分或课程权益回收／保留事实；M09 单独记录佣金冲正。
2. 权益已经使用时不得删除历史使用记录来制造“未使用”。
3. 无法完整回收时，应记录未回收原因、余额影响和人工处理结果，不把退款状态伪装成所有权益均恢复。
4. 退款失败不得提前回收全部权益；风险控制措施需明确且可申诉。

### 9.4 佣金形成与冲正（GLB-030）

1. 平台订单佣金只能基于 M08 的真实、有效、可归因订单形成；初期外部成交不得生成平台订单佣金。
2. 访问、注册或下单归因不等于佣金已确认；佣金至少区分候选、待确认、可结算、已结算、退回／冲正等业务阶段。
3. 退款、订单失效、作弊判定或归因纠正可触发佣金退回／冲正，但不得覆盖原佣金记录。
4. 已结算后发生退款的处理方式涉及追扣、负佣金或后续抵扣，需在 M09 PRD 提供方案并确认。
5. 佣金不能直接冲抵用户积分；是否允许佣金兑换积分是独立商业决策。

当前 M09 不处理平台订单佣金，推广合作、老师合作费用、佣金打款和其他结算均在线下合同／财务或第三方渠道完成。

### 9.5 当前资金流边界（GLB-038、GLB-039）

1. 当前面向用户只销售积分包，不销售会员。
2. 收款、退款、老师合作费用、推广佣金打款及其他真实资金结算全部在线下或第三方渠道完成。
3. 产品只记录与当前积分入账／扣回直接相关的外部凭据和账本结果，不建立平台订单、支付、退款或佣金打款事实。
4. M08、线上资金和平台佣金保留在完整蓝图中；只有线下流程无法承接业务规模，且支付、退款、分销及相关合规评估完成后，才重新决定启用。

## 10. 状态关系与非等价规则

### 10.1 创作与任务状态

| 上游／表面状态 | 不等于 | 正确关系 |
|---|---|---|
| 画布已保存 | 生成请求已提交 | 画布只是创作上下文；须由用户确认生成 |
| 任务卡已创建 | 供应商已接受任务 | 卡片是投影；以 M04 的提交事实为准 |
| 删除任务卡 | 任务已取消 | 必须向 M04 单独申请取消并等待明确结果 |
| 用户已请求取消 | 供应商已取消 | 在确认前任务仍可能继续执行和产生结果 |
| 供应商显示成功 | 结果已可靠交付 | M04 仍需取得可持续访问的交付副本 |
| 交付副本已取得 | 用户已保存作品 | M06 只有在用户主动保存后才建立作品 |
| 作品已保存 | 作品已公开 | 作品默认私有，公开需要发布记录和必要审核 |
| 作品已隐藏／撤下 | 文件已永久删除 | 只改变可见范围；删除和保留另行处理 |
| 项目已归档 | 项目内任务已取消 | 运行事实继续由 M04 管理 |

### 10.2 素材、授权与安全状态

| 上游／表面状态 | 不等于 | 正确关系 |
|---|---|---|
| 文件上传成功 | 素材可用于生成 | 还需归属、授权、安全和格式／能力校验 |
| 厂商资产出现在列表 | 厂商资产实际可用 | 以详情状态和当前权益为准 |
| 厂商审核／认证通过 | 平台确认权属合法 | 用户仍对所需权利负责，M14 保留授权记录 |
| 蒙版／模糊已处理 | 已匿名化或可绕过真人限制 | 仍可能识别个人，且不能替代授权或供应商可信资产流程 |
| 素材可用于课程练习 | 素材可公开下载或商业复用 | 使用范围由练习素材授权决定 |
| 授权已撤回 | 所有历史记录立即删除 | 停止新使用；历史任务、作品和审计按对象规则处置 |

### 10.3 积分、订单与权益状态

| 上游／表面状态 | 不等于 | 正确关系 |
|---|---|---|
| 报价已展示 | 用户已确认或已扣费 | 只有确认后才进入可计费流程 |
| 积分已预占 | 积分已实结 | 最终依据任务与交付结果结算 |
| M11 已登记外部成交并执行人工入账 | 积分已到账 | 只有 M07 生成账本事实才算到账 |
| 线下成交已完成 | 平台订单已支付 | 初期只形成发放凭据，不创建 M08 事实 |
| 订单已支付 | 所有权益已到账 | 各权益模块分别确认发放结果 |
| 用户购买积分包 | 用户是会员 | 当前不启用会员，积分包只产生积分入账 |
| 用户有课程权 | 拥有模板、素材或生成额度 | 四类权益分别授予 |
| 订单被归因 | 佣金已确认 | M09 仍需等待有效性和退款条件 |
| 退款已完成 | 所有权益与佣金已回收 | 各模块分别产生回收／冲正事实 |
| 外部退款已确认 | 平台退款已完成 | 当前只登记外部退款凭据并由 M07 扣回积分 |
| 积分扣回后余额不足 | 余额应强制归零 | 保留真实负余额，暂停新的付费生成，新积分优先填平 |

### 10.4 通知、客服与报表状态

| 上游／表面状态 | 不等于 | 正确关系 |
|---|---|---|
| 通知已送达／已读 | 业务成功或用户接受结果 | 源业务状态仍由事实模块定义 |
| 工单已关闭 | 关联任务、积分或订单已修复 | 关闭前应引用源模块处理结果；重新发现问题可再开 |
| 报表显示差异消失 | 源账本已修正 | 差异必须由源模块通过正式事实纠正 |
| 后台显示“处理完成” | 源业务已变更 | M11 只能根据事实主责模块返回结果更新待办 |

## 11. 记录、版本与可追溯要求

### 11.1 最小关联要求（GLB-033）

每次关键业务变化应按相关性关联：

- 业务对象及其所有者／作用范围；
- 发起用户、后台操作者、角色和必要的复核者；
- 来源项目、画布、工作流版本、工具版本或课程／订单；
- 使用的素材、厂商资产及授权状态引用；
- 模型厂商、供应渠道、精确版本和能力快照；
- 报价版本、预计积分、预占、实结、退回或冲正记录；
- 外部任务／订单／支付／资产标识的受控引用；
- 状态变化、失败分类、人工处理和最终结果；
- 当时适用的业务规则与治理决定版本。

“关联”是业务可追溯要求，不代表必须把所有内容复制到同一记录中。敏感素材、授权凭证和供应商原始错误应按最小权限访问。

### 11.2 历史规则版本（GLB-015、GLB-035）

1. 模型能力、报价、工具、课程、商品、佣金、授权和治理规则均应有明确生效范围或版本语义。
2. 新规则只影响明确生效后的新业务事实，除非变更方案明确要求迁移历史且已获批准。
3. 历史任务按提交时的能力、工具和报价规则解释；历史订单按下单／支付时的商品及权益快照解释。
4. 后台修改当前配置不得让历史用户界面显示为“当时就适用新规则”。
5. 紧急安全规则可以阻止后续访问或使用，但不应删除过去发生的事实；需记录生效原因、时间和影响范围。

### 11.3 账本与修正

1. 积分、订单、退款、佣金、权益和审核决定发生错误时，以追加纠正、撤回、冲正或新决定修复，不覆盖原事实。
2. 用户可见页面可展示当前有效结果，但客服和审计必须能还原变化链。
3. 报表发现差异后，将问题交回源事实模块；M13 不创建“报表专用修正值”掩盖业务差异。

### 11.4 软删除与隐私治理（GLB-014）

普通业务对象删除统一采用软删除。软删除后停止正常展示、搜索、新业务引用和用于新生成任务，只允许资源所有者或受控后台角色按权限恢复。

以下动作不得共用一个模糊的“删除”状态：

| 动作 | 业务含义 | 主责 |
|---|---|---|
| 从画布移除 | 不再在当前画布显示或引用 | M01 |
| 取消任务 | 请求 M04 停止执行，结果取决于实际能力 | M04 |
| 素材软删除／失效 | 停止正常展示、搜索、新引用和新生成任务使用；保留受控恢复与必要追溯 | M05/M14 |
| 厂商资产撤回／失效 | 停止目标渠道使用；外部删除能力取决于厂商 | M05/M14 |
| 作品隐藏／撤下 | 降低或停止对外可见，不等于删除私有作品文件 | M06/M14 |
| 作品软删除 | 停止正常展示、搜索、新引用和新发布；保留受控恢复与必要追溯 | M06/M14 |
| 账户注销 | 账户进入治理流程，各资源模块分别处理 | M02/M14 |
| 审计记录到期处理 | 按必要性、争议、法规和安全规则处理 | M11/M14 |

永久删除或匿名化不通过普通删除功能执行，只能进入独立的隐私与治理流程。积分账本、任务、外部交易凭据和其他历史事实不能通过软删除破坏账务与业务追溯。软删除后的具体保留期限及外部厂商数据处理仍待 M14 与各对象主责模块确认。

## 12. 文档冲突与规则变更

### 12.1 冲突判定（GLB-034）

以下情况视为需求冲突，而不是分模块自由发挥：

- 同一对象在不同文档中有两个事实主责；
- 同一状态名称表达不同业务结果；
- 分 PRD 让横向模块直接改账、改订单或改任务；
- 分 PRD 将建议／待确认规则写成已批准；
- 分 PRD 因首发暂缓而删除完整范围中的模块或对象；
- 分 PRD 的角色权限突破私有默认、最小权限或授权范围；
- 外部资料变化后，某文档仍把失效能力写成已支持。

### 12.2 冲突处理流程

1. 发现冲突的文档记录：冲突规则／对象、涉及文档、用户影响、当前实现或需求影响、可选方案和推荐方案。
2. 为冲突分配 OPEN-* 或需求变更记录，不直接覆盖上游文档。
3. 在决策完成前，继续采用总 PRD 和本文当前有效规则；涉及安全、扣费或权限风险时，相关新能力保持关闭或待核验。
4. 决策后先更新总 PRD／本文及变更记录，再更新所有引用分 PRD。
5. 只更新一份分 PRD、不处理其他引用，不构成新版规则生效。

### 12.3 规则变更生效

规则变更记录至少说明：

- 变更原因和决策人／决策来源；
- 新旧规则 ID、版本和生效时间；
- 影响的新请求、在途任务、历史任务、积分、订单、权益、作品和报表；
- 是否需要用户重新确认、通知或申诉入口；
- 是否需要对账、补偿、冲正或人工处理；
- 涉及哪些总分 PRD 和验收场景。

未明确历史影响时，默认不重写已完成的历史事实。
