## 1. 信息分类与调研方法

### 1.1 信息分类

| 标记 | 含义 |
|---|---|
| **用户已明确** | 由用户直接确认的范围或约束，不需用外部资料代替 |
| **已核验事实** | 能由查询日当日可访问的官方文档、官方仓库或固定提交支持 |
| **设计建议** | 根据已核验事实对本产品的需求推导，不是外部产品事实 |
| **待核验／待确认** | 公开资料不足、需账号／商务洽谈／实际调用，或必须由用户做决策的内容 |

### 1.2 取证原则

1. 开源能力以官方仓库的固定提交、README 和 LICENSE 为准；截图、演示和文字声明只证明存在候选能力，不证明生产可用。
2. 模型能力以模型厂商的官方模型页、API 文档和官方仓库为准；不以聚合平台、第三方教程或 Toonflow 界面中出现的名称证明官方适配。
3. 开源软件授权、模型权重授权和云 API 服务条款是三类不同问题，不互相代替。
4. 本文中的“可复用”不等于已经通过本产品的生产验收；许可证结论必须绑定具体仓库与固定提交，不能从旧提交推断新提交，也不能从新提交倒推旧版本。

## 2. 结论摘要

1. **第一轮的 14 个模块已覆盖用户明确要求的完整业务范围**，且订单、分销、课程等暂缓模块仍留在完整蓝图中。初期“线下／其他渠道成交→后管手工加积分”的新约束也已反映到 M07、M11 和分期。
2. **当前模块划分没有明显重复或无人主责的主链环节**，但后续总 PRD 应进一步锁定 M11 “发起／审批”与 M07 “记账／冲正”的唯一主责，以及 M04 “原始交付”与 M06 “长期作品”的交接。
3. **2026-09-28 已确认直接复用 Toonflow-app 的当前技术栈与应用级创作内核。** 实现基线固定为 `master` 提交 `d86cce6b689916ab73f75bc4c1f42a2a7424516c`；该提交根许可证为 MIT，仓库为 workspaces 单仓，Web 端采用 Vue 3、Vite、Vue Flow、Pinia，服务端采用 TypeScript、Bun、Express。选型确认不等于生产验收完成。
4. **React Flow 自研仍保留为 2026-09-23 的可行性研究结论，不再是当前并行首发路线。** vibecoding 能加快画布骨架和重复实现，但不会消除业务语义、任务一致性、恢复、性能和长期维护成本；只有固定 Toonflow 基线出现不可接受的阻断时，才重新进入决策。
5. **许可证事实发生过版本变化，必须分开记录。** 2026-09-23 核验的旧固定提交包含 Apache-2.0 正文及额外商业条款；2026-09-28 选定的固定提交根 `LICENSE` 为 MIT。旧证据是历史快照，不再作为当前基线需要书面商业授权的依据；当前仍须保留 MIT 声明，并审计依赖、内置素材、品牌标识和外部服务各自的权利边界。
6. **Seedance 的厂商素材库应作为 M05 的独立子域，不能和普通上传文件混为一类。** 官方文档显示它包含素材组、素材资产、真人授权／认证、异步入库、可用状态、配额／权益和到期回收，并以 `asset://<asset_id>` 引用到生成请求。
7. **候选模型名称必须落到“厂商—采购渠道—精确模型 ID／快照—能力”后才能开放给用户。** `Nano Banana` 当前是多个 Gemini 图像模型的系列名；MiniMax H3 同时有云 API 和开放权重路径，本项目只应核验云 API；GPT Image 2 是有效模型 ID，但官方已发布更新代际，所以仍不能把候选名写成最终选型。
8. **M04 不应用一套假定强行描述所有模型。** 视频生成常见创建任务后查询状态，图像生成则可能在单次响应或流式响应中返回数据。产品可以统一用户可见状态和异常恢复原则，但必须保留供应商原始状态、错误和结果有效性差异。

### 4.2 画布复用结论

**已核验事实：** Toonflow 确实已展示一套超过底层画布组件的短剧生产应用，且包含资产、模型选择、任务和结果相关业务结构。Open Canvas 是更通用的自由工作流画布，但公开版明确是 alpha、local-first。火宝短剧更适合对照线性的剧本—分镜—成片流程。

**设计建议：**

- 继续保持 M01 “应用级复用优先”，但把复用对象限定为创作工作台的业务交互：项目恢复、资产选用、模型／参数操作、任务占位、结果回填和继续创作。
- 将“自由画布”与“按剧集／剧本／分镜生产”定义为两种用户任务模式。在目标用户未证明为短剧团队前，不要将导入小说、生成剧本或拆分镜设为所有人的必经步骤。
- M02、M07–M14 继续由本产品自主设计；候选仓库中的登录、供应商配置或任务列表不能替代本产品的多用户权限、积分账本、手工发放、客服、报表和治理责任。

**历史阶段待核验项：** 当时尚待确认 Toonflow 的书面商业授权、最终固定版本、标识范围、第三方依赖、Web 多用户场景、画布数据迁移和最小可复用切片。版本与根许可证已在 4.4 节解决；其余仍需进入实施验收。

| 画布骨架 | **高** | 节点外壳、端口、工具栏、拖放、缩放、选中态、右键菜单、快捷键、属性面板和基础保存恢复 | 交互一致性、边界场景、浏览器／触屏验收和无障碍验收 |
| AI 业务节点 | **中高** | 按既定规格批量生成提示词、素材输入、模型选择、生成中、结果等节点的界面与重复逻辑 | 节点职责、输入输出契约、参数约束、模型能力差异及错误语义 |
| 项目保存与恢复 | **中** | 自动保存流程、序列化适配、迁移脚手架和测试样例 | 数据版本策略、资源引用完整性、并发覆盖、损坏恢复和可追溯性 |
| 生成任务与结果回填 | **中** | 状态展示、轮询／通知适配样板、失败提示和结果卡片 | 幂等提交、重复扣费防护、页面关闭后恢复、供应商差异、临时结果转存和异常补偿 |
| 大画布性能 | **低到中** | 根据已知规则完成组件记忆化、懒加载和渲染优化的初稿 | 找出真实瓶颈、建立容量基线、媒体节点内存管理和持续回归 |
| 实时多人协作 | **低** | 生成同步层接入样板和多人光标等可见功能 | 冲突模型、权限、房间生命周期、离线重连、历史一致性和运维可靠性 |

这里的“高／中／低”表示相对加速空间，不是质量等级，也不是开发排期。vibecoding 最适合在业务边界已经明确时生成重复实现、范例改造和验证用例；若节点契约、保存语义或任务状态仍未确定，它只会更快地产生需要返工的实现。

#### 4.3.3 建议的受控首发边界

若选择 React Flow 自研，建议首发只承诺单人编辑和生成主链：创建／打开项目、核心输入与生成节点、连接与校验、画布导航、复制粘贴、基础撤销重做、自动保存与恢复、任务状态回填、结果转为作品。以下能力保留在完整规划中，但不因 vibecoding 看起来容易而自动纳入首发：

- 实时多人协作、评论和复杂冲突合并；
- 任意嵌套子流程、自由白板绘制和高级自动布局；
- 无上限节点规模、重媒体同时播放和复杂连线动画；
- 允许第三方自定义节点或执行任意工作流。

#### 4.3.4 与 Toonflow 复用路线的判断

| 判断维度 | Toonflow 应用级复用 | React Flow 自研应用级画布 |
|---|---|---|
| 首个完整短剧流程 | 更有优势，已有小说—剧本—分镜—制作结构 | 需自行定义和实现，但可以只做本产品真正需要的路径 |
| 通用创作适配 | 可能需要拆除或弱化既有短剧结构 | 更容易围绕自由画布和本产品节点语义设计 |
| 商业授权确定性（2026-09-23 快照） | 当时固定的 Toonflow 旧提交存在需书面确认的附加商业条款 | 核心库为 MIT；Pro 内容需另行核验 |
| 与 M02–M14 的耦合 | 需识别并替换候选项目既有账户、任务和供应商假设 | 从一开始按本产品的权限、积分、素材和任务边界连接 |
| vibecoding 加速空间 | 主要用于理解、裁剪、改造和补齐既有系统 | 主要用于快速搭建画布骨架、业务节点和测试；需求越明确，加速越明显 |
| 主要风险 | 授权、既有架构依赖、版本分叉和产品流程不匹配 | 低估应用层深度、保存恢复、任务一致性、性能和长期维护 |

**截至 2026-09-23 的设计建议：** 当时建议将两条路线放进同一验收表比较，而不是仅比较“能否拖节点”。该建议已被 2026-09-28 的用户决策取代：首发不并行开发 React Flow 路线，本节仅保留为备选路线的可行性证据。

### 6.3 统一产品语义与供应商差异

**设计建议：** M03 应对每个可用组合保存一份可追溯的“能力快照”，其业务语义至少包含：

- 用户展示名、厂商、采购渠道、精确模型 ID／固定快照和可用地区；

- 是同步响应、流式响应还是异步任务，能否查询、回调、取消或使用原任务重试；

M04 对用户提供的状态可统一为“校验中、等待提交、已提交、处理中、交付中、成功、失败、已取消”等产品层语义，但本轮不将此建议写成已确认完整状态机。任务记录应保留供应商原始状态与错误，且只有供应商确认支持时才向用户展示取消或原任务重试。

**结果交接建议：** “供应商返回结果”、“本产品已取得可持续访问的交付副本”和“用户已保存为作品”是三个不同事实。M04 主责前两者，M06 主责第三者；不能将临时 URL 或当次 API 响应直接视为长期作品库。

### 11.2 设计建议与职责影响

1. 将候选能力统一命名为“隐私遮挡与区域编辑工具”或“蒙版编辑”，用于遮挡无关路人、车牌、屏幕／文档敏感信息、标记局部重绘区域以及经授权的局部编辑。
2. M01 主责工具定义、工具版本、画布节点和用户编辑体验；M04 主责工具运行、阻断／失败事实和结果交付；M05 主责原素材、派生素材与真人授权记录；M03 主责按厂商—渠道—精确版本维护真人能力；M14 主责授权、安全、AI 标识、举报和审计规则。
3. 提交前按四个维度预检：素材来源、用途范围、授权状态、供应商能力／可信资产前置条件。来源不明、授权撤回／过期或高风险场景不得自动提交。
4. 对模型能力只展示“支持已授权真人输入”“仅支持供应商可信资产”“不支持真人输入”“尚未核验”等可核查状态；“本产品能编辑蒙版”不代表“模型接受编辑后的素材”。
5. 失败说明只告诉用户合法下一步：补充授权、完成供应商可信资产流程、选择明确支持且符合条件的渠道、改用虚拟角色或转人工复核。不得暴露审核阈值或给出规避建议。
6. 原素材与派生素材、权利声明、目标渠道、模型版本、提交／阻断／审核和结果应可追溯；普通日志不得暴露敏感内容或凭证。

### 11.3 待确认

- 首发是否完全禁止未成年人真人素材；当前建议默认禁止，直到有专门法律评估和监护人授权流程。
- 产品是否保存授权凭证原件，还是只保存声明与凭证引用。
- 隐私遮挡首发只处理图片，还是覆盖视频逐帧／跟踪与音频；后两者会显著增加复核和隐私风险。
- 产品是否自行执行人脸检测、身份比对或活体认证；若会，需要专项评估必要性、告知同意、影响评估及可能的备案义务。
- 各首发模型渠道对真人输入、可信资产、未成年人、公共人物、声音和 AI 标识的精确要求。
